# Platform

About `sys.rs` and `sys/` (`ax.rs`, `place.rs`, `hotkeys.rs`, `keys.rs`, `snap.rs`, `footprint.rs`, `status_item.rs`), the start-up in `main.rs`, `macos/Info.plist`, `scripts/dev-app.sh`: every call to macOS, and what happens elsewhere.

## Rules

- **The main thread never waits on another app.** Each step of a move is a question to the app in front, which may hang: the move runs on the background executor (`Mado::run`), and every question gives up after a quarter of a second, set once for the process on the system-wide element (`sys::limit_waits`). A timeout set on one app's element covers that element alone; its windows would wait the system's six seconds.
- **Mado's own window is moved on the main thread, outside any update of the app.** Accessibility answers a question to the app's own process in that process, and sets a frame through AppKit there; from the background executor that stopped the app at `-[NSWindow _setFrameCommon:]`. `place::front` refuses Mado's own window off the main thread (`Refused::Ours`), and `Mado::run` moves it again with `sys::place_own` in its task's own body, which only tries the memory's lock, so the main thread never waits on another move. Inside `this.update` gpui could not take the window's resize as it happened, and the settings kept their old drawing stretched over the new frame.
- **A drag of Mado's own window is watched by the app itself.** AppKit's global monitor reports other apps' events alone, so the settings window's drag never reached it, and a placed settings window kept its size. The window's top starts the drag (`Mado::own_drag_began`), and a task reads the pointer a frame at a time while the button is held, then restores on the main thread outside any update (`sys::own_dragged_away`). Over a snap area it shows the footprint, and let go there, the window is carried there as a shortcut carries it, 50 ms after the release so the window server's last move is behind it (`sys::own_snapped`). Left out, a person trying snapping on the settings window, the one in front as Snap Areas is turned on, found that nothing snapped at all.
- **A drag is watched off the main thread.** AppKit's global monitor reports the left button and the keys on the main thread, where they are only read and handed to a thread of its own (`snap.rs`); that thread asks Accessibility which window is under the press and where it is at each drag. The footprint's news comes back down a channel and is drawn on the main thread (`sys::footprint`).
- **The screens are read on the main thread** (`place::screens`), where AppKit keeps them; it is a read of what AppKit holds and asks no other app.
- **The shortcuts are Carbon's hot keys** (`RegisterEventHotKey`), the system's own way for an app to answer a key from anywhere: no permission, no event tap, and no key but the shortcuts reaches Mado. An event tap would need Input Monitoring and would hold every key on the Mac while Mado's main thread was busy. The press arrives on the main thread through the app's event target and goes down a channel as the action's number.
- **A shortcut is recorded from AppKit's key event**, not gpui's (`keys.rs`, a local monitor): its key code and flags are the numbers a hot key is registered with, whatever layout is in use. While nothing is recorded the monitor passes every event on.
- **Accessibility is the one permission.** Whether it is given is whether the app in front can be asked for (`ax::trusted`): an answer of `kAXErrorAPIDisabled` says no, a success says yes, and only an answer that says neither falls to `AXIsProcessTrusted`, which answers a running process with its launch-time value.
- **Allow forgets the system's old entry first** (`tccutil reset Accessibility <bundle id>`, no `sudo`), then asks the system's question. The system binds a grant to the app's signature: an entry made for a copy signed otherwise shows as on and counts for nothing. Pressed again, Allow opens System Settings at Accessibility.
- **Accessibility is asked about, never polled**: when the settings open or come back in front, after Allow, and at each of the system's notices (`com.apple.accessibility.api`), which come a moment before the change is written, so a notice is followed by a few tries a quarter second apart (`check_trust_soon`). When it is given after Allow, the settings come back in front.
- **One Mado runs at a time.** A Mado opened while another runs, release or dev, asks it to quit and makes it a few seconds on (`sys::end_other_copies`): two would each hold the shortcuts. A probe copy, with a `MADO_HOME` of its own, ends none and holds no shortcut.
- **Settings close by `on_window_closed`**, never `on_window_should_close`, which ⌘W never asks. Closing puts Mado back out of the Dock and gives up a recording.
- **The app in front of a move** is the workspace's (`NSWorkspace::frontmostApplication`, `place::front_app`), and its window the one it says has focus, else its main one, else its first standard window (`place::front_window`). The system-wide element's `AXFocusedApplication` asks the app in front for its focus, and fails with `kAXErrorCannotComplete` while that app's focus cannot answer (Emaki, in some of its sessions), though its windows can: asked first, a shortcut did nothing there until the app's focus moved. A move that finds no window logs the error that ended the search.

## Snap areas

- **Where a press was is the event's own place** (`locationInWindow`, a global event's place on the screens), never where the cursor is as the event is read (`NSEvent::mouseLocation`): handed on a beat late, a press read where the cursor had gone was taken for a press on the window under it then, and the drag of the window pressed went unwatched.
- **Which window a drag holds** is the window server's topmost at the press (`ax::window_under`, front to back, an app's own windows), found among its app's windows by its number; Accessibility's hit test (`AXUIElementCopyElementAtPosition`) stands in only where the number cannot be had. It is asked again up to 20 times, a tenth of a second apart, for an app slow to answer. Mado's own windows are left to the app's own watch.
- **Moving, not resizing**: the window's place changed and its size did not, or did with fewer than two edges where they were. A window resized by an edge keeps two, and is never snapped.
- **Dragged away**: once the cursor is 30 points from the press (`layout::AWAY`), a window Mado placed takes back its size (`Memory::dragged`), set by Accessibility while the drag goes on; the window server keeps dragging it from where it is. Asked at the first move instead, a nudge undid a placed window.
- **A window is put in its place at once**, as Rectangle's are (`place::apply`): no glide. Moved a step a frame by Accessibility, a window shows each step only once its app has drawn it at that size, and while the app draws its main thread answers nothing, a new position included. Screen recordings at 60 a second showed every step only for an app that draws in a frame; one taking 25 ms showed about two in three, and Emaki at half a screen takes 7 to 33 ms to show a new size. Pacing the steps by a display link was the best of every way tried (a sleep's timing, the size a frame ahead, waiting for each size, the position alone each frame), and still stepped on such apps. `AXFrame` cannot be set, so position and size are two calls. A plate of Mado's own sliding over the window, behind it or ahead of it, read as a stand-in and was dropped.
- **macOS's own command moves a window over a moment** (`place::by_command`): macOS 15 puts Move & Resize in every app's Window menu (Left, Right, Top, Bottom, Fill, Center, Return to Previous Size), and chosen there the app animates its own window, drawing every step, as macOS's own tiling does: 20 steps a frame apart, about 330 ms, measured on a test window. Mado chooses the item through Accessibility (`AXPress`) for a half, Maximize (Fill), Center and Restore (Return to Previous Size), from a shortcut, the menu or a snap. The item is named by its key equivalent, fn ⌃ with an arrow or F, C or R (`AXMenuItemCmdModifiers` 28), the same in every language; it is searched from the app's last menu back and kept by app. The move's thread waits until the window is still for three frames (a second at most) and notes the frame it came to; an app without the item, a window it does not move within a fifth of a second, and every other action are put at once. Restore is put again where the system's previous size is not where Mado would put it. Mado's own window is carried by AppKit instead (`place::own_animate`, the window's animator in an `NSAnimationContext`) over the same 350 ms on a curve fitted to a window the system tiled (cubic-bezier 0.3, 1, 0.3, 1), for every action, Restore included, and for a snap: the main thread never waits for a command, an app pressing its own menu through Accessibility is refused, and the system's Return to Previous Size goes to the size the system kept, not Mado's. It is noted at the frame asked for and, once still, at the frame it came to (`sys::own_settled`, `Memory::settled`).
- **An app's Window menu has Move & Resize only when AppKit knows it as the Window menu** (`NSApp.windowsMenu`). gpui marks a menu so only when it is titled "Window" in English; Mado's is in the person's language, so it had none, and an app built the same way has none either, so its windows move at once. `sys::mark_windows_menu` marks it by its title each time the menus are set (`set_app_menus`).
- **Let go over an area**, the area is asked again at the release (the last drag event may be behind it) and the window is placed (`place::snapped`), on a thread of its own so the next drag's events wait on nothing. It waits until the window's frame reads the same twice a frame apart (a fifth of a second at most), puts it, and puts it again if it is moved off within the next 120 ms: an app that drags its own window may move it once more after the release, and put there before that, the window stood off its place and the place noted for it was not where it stood. Esc during the drag gives it up.
- **macOS's own tiling takes the same drags** (macOS 15 and later: Desktop & Dock's "Drag windows to left or right edge of screen to tile" and "Drag windows to menu bar to fill screen"). With it on, a drag to an edge is tiled twice, and macOS's restore fights Mado's. `sys::system_tiling` reads `EnableTilingByEdgeDrag` and `EnableTopTilingByEdgeDrag` from `com.apple.WindowManager` (a switch never touched is on), off the main thread, at launch and each time the settings come back in front; Snap Areas says so and opens Desktop & Dock (`sys::DESKTOP_SETTINGS`). Mado leaves the setting to the person.
- **The footprint** (`footprint.rs`) is a borderless window over every app at the modal panel's level, on every Space, that ignores the pointer, holding an `NSVisualEffectView` at part strength under an `NSBox` with a breath of lilac and a hairline of it, rounded 12 (`docs/design.md`, The footprint). It grows from the dragged window's frame (`Footprint::Show`'s second frame: the drags' thread keeps the window's last frame, and Mado's own drag reads its own window) as it fades in over 280 ms, slides to the next area over 220 ms, and fades out over 160 ms, on the studio's curve, made by name (`CAMediaTimingFunction`, `functionWithControlPoints::::`, a selector `msg_send!` cannot name). Faded out it stays ordered in at no opacity, so showing it again is one change. Its shade follows the system's appearance.
- **Drags are watched** while Accessibility is given and the app in front is not ignored (`SnapState::on`), with snapping on or off, since a placed window always takes back its size when dragged away; a probe copy watches none. Snapping off, a watched drag shows no footprint and snaps nowhere, and a placed window dragged away still takes back its size.

## Tilings

- **Which windows are on a screen** is the window server's answer (`CGWindowListCopyWindowInfo`, on screen, desktop left out): each window's app and number, front to back, for the Space in front. It asks no app, so it answers at once. Each app with one of them is asked for its windows (`AXWindows`), and a window counts when its number is in the list, it is a standard window, not minimized and not full screen, and most of it is on the screen. An app's windows alone, from Accessibility, would bring those of other Spaces and the minimized.
- **It runs on the background executor**, as a move of the window in front does, and leaves Mado's own windows where they are.

## The menu bar and the Dock

- **`LSUIElement`** is in every bundle's `Info.plist` (the release's from `macos/Info.plist`, the dev build's from `dev-app.sh`), and `sys::stay_in_menu_bar` says it again at launch, since gpui makes every app a regular one as it starts.
- **While the settings are open Mado is in the Dock** and ⌘-Tab, with its own menus (`sys::in_dock`), so the window is found again once another app covers it.
- **The item** (`status_item.rs`) is the icon's window as a template image, 18 points, which the system tints. It has no menu of its own: the button sends both clicks to a target, which opens the settings, or builds the menu from the lines the app last handed over (`set_menu_lines`), sets it, clicks the button and takes it off again. The app hands new lines whenever what they say changes: a shortcut, the language, the app in front.
- **The menu's pictures** are the window's SVGs (an action's 18 by 12, an icon's 16 square) drawn by resvg into template images, each once and kept, and each line asks for its image (`preferredImageVisibility`), or an app built on the macOS 27 SDK shows names alone. A line's shortcut is its key equivalent: AppKit's character for the key (the arrows are `U+F700` to `U+F703`) and the event's own modifier flags. A line chosen moves the window in front, which stays in front: a menu bar item's menu does not take the app's place.
- **The app in front** is watched (`NSWorkspaceDidActivateApplicationNotification`) for the menu's Ignore line; Mado's own activation leaves the app before it as the one named. While an ignored app is in front, no shortcut is held and no drag snaps.
- **Opened again** from Finder or Spotlight while running, Mado shows the settings, the way back with the item hidden.
- **The first launch shows the settings**, where Accessibility is allowed (`UiState::opened`); later launches start in the menu bar.
- **Launch at login** is the system's (`SMAppService`), read when the settings open or come back, never written to the config.

## Dev builds and signing

`scripts/dev-app.sh` puts the build in `target/debug/dev.noindex/Mado.app` with its own identifier, `com.alkalinesoftware.mado.dev`, signed with the developer's identity when the keychain has one. Accessibility is bound to the signature, so a build signed by nobody is a new app to Privacy & Security after every build, and a bare binary run from a terminal is the terminal as far as the system is concerned.

## Gates

Mado is published for the Mac alone. The code builds elsewhere, and each function in `sys.rs` says what happens there:

| Function | Elsewhere |
|---|---|
| `screens`, `pointer`, `place_front`, `place_own`, `tile_windows` | no screens, the pointer at the origin; every move is refused (`Refused::Elsewhere`) |
| `trusted`, `ask_trust`, `trust_changes` | given; nothing to ask; no notice |
| `install_hotkeys`, `set_hotkeys` | no presses; nothing held |
| `install_key_watch`, `record_keys` | no keys recorded |
| `install_menu_bar`, `set_menu_bar`, `set_menu_lines` | no item; the settings open at every launch |
| `install_snapping`, `footprint` | no drag is watched; no footprint |
| `front_apps`, `cursor_to` | no app in front; the cursor stays |
| `in_dock`, `end_other_copies`, `launches_at_login` | nothing; nothing; no |
